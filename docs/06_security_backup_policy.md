# 보안 및 백업 정책서

## 1. 보안 기본 원칙

내부용 서비스라도 로그인과 권한 관리는 반드시 적용한다. 재고와 출고 이력은 회사 운영 데이터이므로 외부 노출과 데이터 유실을 방지해야 한다.

## 2. 계정 보안

- 모든 사용자는 개인 계정으로 로그인한다.
- 공용 계정 사용은 지양한다.
- 관리자 계정은 최소 인원에게만 부여한다.
- 퇴사자 또는 업무 변경자는 계정을 비활성화한다.
- 초기 비밀번호는 운영 전 반드시 변경한다.

## 3. 권한 정책

| 역할 | 권한 |
|---|---|
| 관리자 | 전체 기능 사용 가능 |
| 주문관리 담당자 | 거래처/주문 관리 가능 |
| 출고 담당자 | 재고 조회 및 출고 처리 가능 |
| 조회 사용자 | 조회만 가능 |

## 4. 데이터 보호

- DATABASE_URL은 서버 환경변수에만 저장한다.
- DB 접속 정보는 GitHub에 올리지 않는다.
- 브라우저에서 DB에 직접 접근하지 않는다.
- Supabase 관리자 키 또는 서비스 키는 클라이언트 코드에 포함하지 않는다.
- 운영 DB는 직접 수정하지 않는다.

## 5. 업무 데이터 삭제 정책

운영 데이터는 삭제하지 않고 상태값으로 관리한다.

| 데이터 | 처리 방식 |
|---|---|
| 항원 | 비활성화 |
| 거래처 | 비활성화 |
| 주문 | 취소 상태 |
| 출고 | 취소 상태 |
| 재고 | 폐기 또는 조정 이력 |

## 6. 감사 로그 정책

다음 작업은 반드시 이력을 남긴다.

- 입고 등록
- 출고 처리
- 출고 취소
- 재고 조정
- 재고 폐기
- 제조번호 수정
- 유통기한 수정
- 주문 취소
- 사용자 권한 변경

## 7. 백업 정책

### 7.1 백업 주기

| 종류 | 주기 |
|---|---|
| 자동 백업 | 매일 1회 |
| 수동 백업 | 배포 전 |
| 월말 백업 | 매월 말 |

### 7.2 백업 보관

- 최소 30일 이상 보관한다.
- 백업 파일은 2곳 이상에 보관한다.
- 월말 백업은 별도 장기 보관한다.

### 7.3 복구 테스트

백업은 저장만 하는 것이 아니라 복구 가능해야 한다. 분기별 또는 주요 업데이트 전후로 복구 테스트를 권장한다.

## 8. 성능/보안 리스크

| 리스크 | 설명 | 대응 |
|---|---|---|
| 동시 출고 | 같은 LOT를 동시에 출고하면 재고 음수 가능 | 트랜잭션과 조건부 업데이트 적용 |
| 환경변수 노출 | DB URL이 외부에 노출될 수 있음 | .env 커밋 금지, Vercel 환경변수 사용 |
| 권한 누락 | 출고 담당자가 관리자 기능 접근 가능 | 역할 기반 접근 제어 적용 |
| 데이터 삭제 | 이력 추적 불가 | 삭제 대신 상태 변경 |
| 백업 누락 | 장애 시 복구 불가 | 자동 백업 + 수동 백업 병행 |
